# 13 历史库改造方案：跨设备变量与时间精度

> **本文是方案，不是已实施的改动。**
> 这两项都要动**表结构 / 落库格式**（历史库 DDL、`SampleTime` 序列化精度），
> 现有 `history.db`（约 24 MB）里已经有现场数据，改坏了没法从老库补回来。
> 所以本轮只把问题、证据、三条可选路线和验收步骤写清楚，等确认后再动手。

---

## 1. 两个问题，一句话版本

| # | 问题 | 现象 | 触发条件 |
|---|---|---|---|
| P1 | 变量字典按 **`VarName` 唯一**，不区分设备 | 两台设备有同名变量时，它们的历史数据被归到同一个 `VarId`，趋势图上把两台设备的数掺在一起 | 同一个 `history.db` 上有 **两个及以上设备**，且变量名重复 |
| P2 | 采样时间只精确到 **秒**，且同秒写入被"去重"丢弃 | 同一变量同一秒内的第二个采样被静默丢掉，`written` 比实际点数少 | 归档周期 < 1 s、重连/故障恢复后补写、迁移老库（老库本身就是秒级） |

## 2. 证据（代码位置）

### P1 变量字典

```text
KyjScada.Domain/History/HistorySchema.cs:38
    VarName TEXT NOT NULL UNIQUE          ← 唯一键里没有 DeviceName
KyjScada.Infrastructure/Data/HistoryRepository.cs:105
    SELECT VarId FROM VarDict WHERE VarName = $n        ← 只按名字查
KyjScada.Infrastructure/Data/HistoryRepository.cs:114/130
    _varIdCache[varName] = id                           ← 内存缓存键也只有名字
KyjScada.Infrastructure/Data/HistoryRepository.cs:41
    Dictionary<string,int> _varIdCache = new(StringComparer.OrdinalIgnoreCase)
```

后果链：

1. 设备 A 的 `Env_Temp` 先落库，拿到 `VarId = 7`，`DeviceName` 记的是 A；
2. 设备 B 的 `Env_Temp` 进来，`SELECT ... WHERE VarName = 'Env_Temp'` 命中 7，**不会插新行**；
3. B 的采样全部写进 `VarId = 7`；
4. `Docs/MCP` 的 `list_variables` 只显示一条，`DeviceName` 恒为 A；
5. 趋势/报表按 `VarId` 查，A、B 两条曲线被画成一条。

**当前现场是否已触发？** 没有。实测当前三个协议配置文件（`ModbusRTU.json` / `ModbusRTUOverTCP.json` / `ModbusTCP.json`）
单文件内**跨设备同名变量 0 个**（139 / 139 / 129 个变量，`DeviceName` 唯一）。
所以这是一个**潜伏缺陷**：现在没事，一旦加第二台设备且名字撞了，历史数据会静默混在一起，而且**事后无法分开**。

### P2 时间精度

```text
KyjScada.Domain/History/HistorySchema.cs:32
    TimeFormat = "yyyy-MM-dd HH:mm:ss"                  ← 秒级
KyjScada.Domain/History/HistorySchema.cs:47
    SampleTime TEXT NOT NULL                            ← 文本时间,按字符串比较
KyjScada.Infrastructure/Data/HistoryRepository.cs:203
    INSERT ... SELECT $t,$v,$val,$q
    WHERE NOT EXISTS (SELECT 1 FROM History WHERE VarId=$v AND SampleTime=$t)
                                                        ← 同变量同秒 → 第二条被丢弃,且**不报错**
KyjScada.Infrastructure/Data/HistoryRepository.cs:212
    pTime.Value = r.SampleTime.ToString(TimeFormat, InvariantCulture)
                                                        ← 毫秒在写库那一步被截断
```

现状参数：采集 1 s 一次、归档 10 s 一次（`KyjScada.Runtime/ArchiveService.cs:13`），
所以**正常运行时**同秒冲突几乎不会发生；真正的风险场景是：

- 归档周期被调小到 < 1 s（`AppSettings.ArchiveIntervalSeconds` 可改）；
- 写库失败后重试（`ArchiveService` 只记 `LastError`，下个周期继续，可能补写同秒）；
- 老库迁移（`KyjScada.Infrastructure/Data/LegacyMigrator.cs:178`，老数据本身就是秒级），
  同一个老时间戳被反复迁移时不重复插入（这个是有意为之，属于 P2 的"期望行为"）；
- 两个 `ArchiveService` 实例（界面 + 后台作业）同时归档。

## 3. 改造方案

### P1：变量字典加设备维度

#### 方案 A（推荐）：`VarDict` 加 `DeviceName` 参与唯一键

```sql
-- 目标结构
CREATE TABLE VarDict (
    VarId      INTEGER PRIMARY KEY,
    VarName    TEXT NOT NULL,
    DeviceName TEXT NOT NULL DEFAULT '',
    Unit       TEXT,
    UNIQUE (VarName, DeviceName)        -- 取代 VarName 单列唯一
);
```

配套改动（共 4 处代码）：

| 位置 | 改什么 |
|---|---|
| `Domain/History/HistorySchema.cs:36-41` | 建表语句换成上面这份；注释同步 |
| `Infrastructure/Data/HistoryRepository.cs:90-134` | `GetOrCreateVarId(varName, deviceName, unit)`：缓存键改成 `(varName, deviceName)`，`SELECT` 与 `INSERT` 都带上 `DeviceName` |
| `Infrastructure/Data/HistoryRepository.cs:310` + `GetVarDict()` | 其余按 `VarName` 查 `VarId` 的地方，取决于调用方**是否知道设备名**：知道就带上，不知道就保持"同名取第一个"并**返回显式警告**，不要静默 |
| `KyjScada.Mcp/Data/DbReader.cs:85-104`、`ReadOnlyTools.cs` | `list_variables` 显示 `(VarName, DeviceName)` 两个字段；工具入参支持可选 `device` 过滤 |

迁移步骤（必须一次性、可回滚）：

1. 停应用、**备份** `history.db`（现场约 24 MB，复制一份即可）；
2. `CREATE TABLE VarDict_new (...)` → `INSERT ... SELECT VarId, VarName, COALESCE(DeviceName,''), Unit FROM VarDict` → 重命名；
   因为老表 `VarName` 唯一，新唯一键 `(VarName, DeviceName)` 一定不会冲突，**历史行不用改**；
3. 校验：`SELECT COUNT(*) FROM VarDict_new` 与老表一致；`SELECT VarId, VarName, DeviceName FROM VarDict_new` 逐行比对；
4. 起应用，观察 `WritePoints` 是否给新设备插了新行、老变量是否仍命中老 `VarId`（不能产生重复变量）。

风险：

- **不可逆点**是 3 步之后的写库；回滚只能靠备份文件；
- 老 `history.db` 里已经混合的数据**无法按设备拆开**（信息已丢失）——这是方案执行前必须接受的现实；
- `DbReader` 的老库分支（宽表 `ActualData`）不受影响。

#### 方案 B：变量名加设备前缀（`设备名.变量名`）

改动最小（只在写入侧拼名字），但：

- `VarName` 变成两个含义（前缀既是名字又是设备），MCP 查询、趋势选择、报警配置全都要跟着改；
- 现场已有的 `history.db` 里存的是**不带前缀**的名字，迁移要在 `VarDict` 里重命名并同步 `History.VarId` 语义；
- 变量名是给用户看的（`LQB1_RunState` 已经很直观），再加前缀会变长。

**不推荐**：等于把 P1 的复杂度转移到所有下游。

#### 方案 C：保持现状 + 启动时告警

只在应用启动/配置加载时检查"同一份配置里是否有跨设备同名变量"，有就弹窗提示"历史库会混数据"。

- 成本 20 行，零迁移风险；
- 但缺陷本身没修，用户只能手工改名绕开；
- 作为**方案 A 的前置补丁**可以接受（先告警，再择期升级表结构）。

**推荐**：先上方案 C 的告警（当天可完成），再按方案 A 做一次计划停机迁移。

### P2：时间精度到毫秒

#### 方案 A（推荐）：`SampleTime` 存毫秒文本 + 保留"同秒去重"作为**显式**行为

```text
TimeFormat = "yyyy-MM-dd HH:mm:ss.fff"       ← 只改常量
```

- 写库时 `r.SampleTime.ToString(NewFormat, InvariantCulture)`，毫秒保留；
- `WHERE NOT EXISTS (... VarId=$v AND SampleTime=$t)` 保留，但语义变成"同**毫秒**去重"，
  重复写入同一条记录仍然幂等（迁移重跑安全）；
- 查询侧（`HistoryRepository` 的时段查询、`TrendChartControl`、MCP `query_history`）：
  **所有按字符串比较时间的地方都要能接受两种格式**——老数据是 19 字符，新数据是 23 字符。
  `BETWEEN $from AND $to` 用文本比较时，`'2026-11-07 10:00:00'` < `'2026-11-07 10:00:00.500'`（字典序成立），
  所以**老数据不需要重写**，只要查询侧把 `$from/$to` 也按同一格式（或直接按秒级格式）传即可；
- 建议同时给 `History` 加组合唯一索引 `(VarId, SampleTime)`，把"去重"从 `SELECT NOT EXISTS`（每行一次子查询）
  变成约束冲突，性能更好。

风险：

- 任何**自己拼时间字符串**的地方（导出 Excel、报表分页、MCP 工具入参）都要检查；漏改会静默查不到数据；
- 老库与新库混用时，同一变量可能出现"秒级行 + 毫秒级行"，趋势图上表现为重复点 —— 需在查询侧按 `VarId + 截断到秒` 去重一次；
- 索引 `idx_history_var_time` 需要重建（23 字符键比 19 字符宽，库会涨一点）。

#### 方案 B：`SampleTime` 改 INTEGER（Unix 毫秒）

- 排序、比较、索引都最快，`DateTime` 转换只有一处；
- 但需要**全表重写**历史库（24 MB，几秒到几十秒），且所有查询 SQL 都要改；
- 老库字符串时间与新库整数时间不能在同一个 `history.db` 里共存（除非加 `TimeScale` 列）。

**不推荐本轮做**：收益（毫秒级精度）与风险（全量重写 + 全部查询改）不匹配。

#### 方案 C：不改表，只在归档侧"拒绝同秒重复"并**计数上报**

- 保持秒级；`ArchiveService.Archive` 里对 `(varName, sampleTime truncated to second)` 做本批内去重，
  冲突时累加 `SkippedSameSecond` 计数器，界面/MCP 能看到"这一秒丢了几条"；
- 零迁移；但不解决精度丢失。

**推荐**：先做 C 的计数器（能立刻知道有没有真的丢数据），再按方案 A 升级精度。

## 4. 建议的执行顺序（如果确认要做）

| 阶段 | 内容 | 停机 | 可回滚 |
|---|---|---|---|
| 1 | P1 方案 C 告警 + P2 方案 C 计数器（纯代码，不动表） | 否 | 是 |
| 2 | 观察一周：`SkippedSameSecond` 是否为 0、有无同名变量告警 | 否 | — |
| 3 | P2 方案 A：改 `TimeFormat` 常量 + 查询侧兼容 + 重建索引 | 否（索引重建期间锁库，建议停应用） | 是（改回常量即可） |
| 4 | P1 方案 A：`VarDict` 加 `DeviceName` 唯一键 + 迁移脚本 | 是（约 1 分钟） | 仅备份 |

> 阶段 3 与阶段 4 可以合并成一次停机窗口，但**不要**和别的表结构改动混在一起做。
