### 依赖规则（改代码时唯一要守的架构约束）

1. **依赖只能向下**：Contracts 不认识任何人；Domain 只认 Contracts；Infrastructure 与 Runtime 只认 Contracts+Domain。
2. **`Runtime` 里不许出现 SQL / 串口 / Socket**。它只操作 `IHistoryRepository` 之类的接口。
   一旦把 `SqliteConnection` 写进 Runtime，`KyjScada.Verify`（引用 Runtime 但无 Sqlite 包）立刻编不过。
3. **`Infrastructure` 里不许出现 `System.Windows`**。它是 net8.0 而不是 `-windows`，物理上做不到。
4. **只有 `App` 能 `new` 具体实现**。Domain/Infrastructure/Runtime 里所有具体类都必须经由接口被使用
   （唯一的例外：Domain 里的协议描述符由 `ProtocolRegistry` 静态登记，见 04 篇）。
5. **`KyjScada.Mcp` 不许引用 Domain/Infrastructure**。它拿不到 `HistorySchema`，所以自己抄了一份表结构
   （`Data\Models.cs`）——这是已知债务，不是风格选择（见 08 篇）。

## 3. 四条数据链路

### 链路 A：采集 → 报警/归档（每设备一条线程，周期 1 s）

```
DevicePipeline.PeriodicLoop()                     [KyjScada.Runtime\DevicePipeline.cs]
   │  ① 等 tick / 检查 Stop
   ├─ ② Service.CollectOnce(bus, now)              [Infrastructure\Acquisition\ModbusAcquisitionService.cs]
   │      · 遍历 GroupList → 按组读保持/输入寄存器（地址由 IProtocolDescriptor 算出）
   │      · ModbusValueCodec 解码（类型 + WordOrder）→ 质量 Good/Bad
   │      · bus.Publish(new ValueSnapshot(version, timestamp, tags))
   │      失败：State="异常"/"未连接"，LastError=原因，不抛异常
   ├─ ③ Alarm.ProcessSnapshot(snapshot)            [Runtime\AlarmService.cs]
   │      每变量一个 AlarmStateMachine（方向+阈值+死区）→ 只在状态**翻转**时产生事件
   ├─ ④ Coordinator.AlarmSink(events)              [由 MainWindow 注入]
   │      → AlarmRepository.WriteEvents(...)       → data\alarms.db
   └─ ⑤ Archive.ShouldWrite(now) 为真时：
          Archive.Archive(snapshot, device)        [Runtime\ArchiveService.cs]
             · 只取 ArchiveEnable=true 的变量（现场 139 个变量里 35 个要存）
             · 跳过 null / Bad / NotCollected / NaN / Infinity ← 表里 Value 是 NOT NULL
             → IHistoryRepository.WritePoints(points) → data\history.db（事务内批量）
```

**为什么报警/归档放在采集线程而不是界面线程**：界面 500 ms 一次刷新，断线时界面会被 WPF 布局占满；
把"判报警""写库"放界面线程会让报警延迟和写库一起卡住。这是老系统最严重的体感问题。

### 链路 B：写入（任何来源都必须过闸门）

```
「参数设置」页按钮 / 「急停·点动」页 / MCP 客户端
        │
        ▼
CommandGate.Write(varName, value, moduleId)     [Runtime\CommandGate.cs，296 行]
   ① Enabled?          否则 WriteVerdict.Disabled
   ② 变量在可写集合里?  否则 UnknownVar / NotWritable（ReasonOf 给中文原因）
   ③ 值合法?            NaN/Infinity → BadValue
   ④ 占用 + 最小间隔     MinInterval 来自 ini 的 WriteMinIntervalMs=800
   ⑤ 审计（WriteAudit：谁/何时/何值/结果）
   ⑥ 下发 → IDeviceWriter.WriteVariable(name, value, out error)
            实现者就是 ModbusAcquisitionService 本身（与读**共用同一个连接**）
        ▼
ModbusFrame 0x06/0x10 → Transport.Send → 等响应 → 回读校验
```

**所有校验都在"下发第一个字节"之前完成**——这是设计目标，不是巧合（`CommandGate.cs` 注释原文）。

### 链路 C：历史查询（趋势页 / 报表页，全在后台线程）

```
用户点「查询」
   → RunTrendQueryAsync()                        Task.Run，界面不阻塞
        → HistoryRepository（读 VarDict 把 VarName→VarId）
        → 参数化 SQL：History h JOIN VarDict d，按 SampleTime BETWEEN @s AND @e
        → TrendAggregator：按分辨率分桶（avg/min/max/首末），数字量按"变位"处理
        → 回 UI：TrendChartControl.SetSeries(...) / ReportGrid.ItemsSource
   → 导出：TrendCsv（CSV）/ XlsxWriter（多列多 sheet 的 .xlsx，无第三方库）
```

报表页的"班次对齐"在 `MainWindow.Report.cs`（`AlignToShiftStart` / `GrainName` / `ReportIntervalSeconds`），
班次小时数来自 ini 的 `ShiftHours=8`、`ShiftStartHour=8`。

### 链路 D：MCP（进程内，Kestrel 线程）

```
外部 AI 客户端 ──HTTP POST /mcp──► McpHost (App\McpHost.cs，static)
                                      │  WebApplication + WithHttpTransport + MapMcp("/mcp")
                                      ├─ ReadOnlyTools → ConfigReader(读 settings\*.json)
                                      │                → DbReader(只读连 history.db / alarms.db)
                                      └─ WriteTools   → writeHandler 委托
                                                        = MainWindow.McpWrite
                                                        → Dispatcher.Invoke → CommandGate.Write(..., "MCP")
```

**`McpWrite` 必须 `Dispatcher.Invoke`**：闸门与采集服务在界面线程创建，写入要串行排队，
从 HTTP 线程直接碰会破坏串行性（代码注释写得很清楚）。

## 4. 线程模型（改代码前先对号入座）

| 线程 | 谁在跑 | 允许碰 | 禁止碰 |
|---|---|---|---|
| **UI / Dispatcher** | 全部事件处理、`OnUiTick`(500ms)、`OnAcqTick`(1s) | 所有控件、`_rows`、`_bus.GetSnapshot()`、`_gate`、仓储调用 | 阻塞 >100 ms 的操作（大查询、`StopAsync().GetResult()`、`Thread.Sleep`） |
| **采集线程**（每设备 1 条） | `DevicePipeline.PeriodicLoop` | 采集服务、`ValueBus`、`AlarmService`、`ArchiveService`、SQLite 写连接 | 任何 `System.Windows` 对象 |
| **Kestrel 线程池**（4~N 条） | MCP 工具方法 | `DbReader`（只读连接）、`ConfigReader` | 控件；要写必须 `Dispatcher.Invoke` |
| **Task.Run 线程** | 趋势查询、MCP 起停、报表导出 | 仓储/纯计算 | 直接改 `ItemsSource`（要回 Dispatcher） |

实测约束（来自 `--ui-diag` 诊断，见 10 篇）：
- `OnUiTick` 单次耗时目标 <100 ms；曾经因为 `ValueGrid.Items.Refresh()` 每次 80~160 ms 造成"卡顿"，
  现在 `ValueRow` 实现 `INotifyPropertyChanged`，**这行必须保持删除状态**。
- `OnAcqTick` 里超过 40 ms 会写 `data\ui-latency.log`。

## 5. 生命周期：启动 → 切设备 → 关闭

```
App.xaml (StartupUri=MainWindow.xaml)
  └─ MainWindow ctor：建 500ms _uiTimer、挂 Loaded/Closed、接图表事件
       └─ Loaded → OnLoaded()
            ① FindSettingsDir()                ← 程序目录\settings
            ② SettingsJsonCodec.LoadDirectory  ← 所有 *.json，取"有设备的项目"
            ③ AppSettings.Load()               ← data\app_settings.ini
            ④ BuildDeviceSelector()            ← 设备下拉（_deviceList）
            ⑤ 选中设备：ui_state.ini 里记住的 → 否则第一个"可采集"的
            ⑥ ApplyDevice(preferred)
                  · OrderBox 设字节序（必须先设 _device 再动 OrderBox）
                  · BuildRows / EnsureDatabases / InitTrend / InitLiveTrend
                    / InitAlarmPage / InitReport / InitUsers
                  · EnsurePipeline → EnsureCoordinator（单例）→ StartAcquisition()
                     → coordinator.Build(_deviceList) + StartAll() + 起 1s _acqTimer
                  · BuildWritePage / BuildJogPage
            ⑦ 页脚写一行"配置: X  设备 N 台  变量 M 个  报警 K  归档 J"
```

**切设备**（`DeviceBox` 变化 → `ApplyDevice`）只做三件事：换 `_device`/`_bus`/`_pipeline`、重建各页绑定、
写入 `ui_state.ini`。**不 Stop 任何流水线**——其它设备继续采（安全要求）。

**关闭**（`OnClosed`）：停 `_uiTimer` → 停协调器（`StopAll`，含等采集线程退出）→ `McpHost.Stop()`。
MCP 的 Stop 是阻塞的，历史上在 UI 线程直接调用过，导致退出/重启卡死；现在一律 `Task.Run`。

## 6. 五条不变量（破坏它们就会出"现场才发现的 bug"）

1. **快照不可变**：`ValueSnapshot` 发布后不修改；界面拿到的永远是某一时刻的完整集合
   （所以不会出现"一半新值一半旧值"的撕裂读数）。
2. **一个变量在一条快照里只出现一次**，且 `TagValue.ChangedAt` 表示"这个值上次变化的时刻"，
   不是采集时刻（界面"时间"列显示的是它）。
3. **写路径唯一**：任何绕过 `CommandGate` 的直接 `transport.Send` 都是 bug（无审计、无权限、无限速）。
4. **归档只见"有效值"**：`History.Value` 是 `NOT NULL`，写 NULL 会让报表出现假 0。
5. **UI 只读流水线状态**，不反向驱动采集：界面可以"看"任何设备，但不能让某台设备停采。
